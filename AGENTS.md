# Работа с bass_study

## Контекст

Это личный локальный бас-тренажёр: основной инструмент E–A–D–G, первая платформа Windows-компьютер с браузером и клавиатурой, приоритет — гриф и основы. Репозиторий: https://github.com/fin4cast/bass_study.

На 2026-11-08 выполнены P0–P6 и P7-00, текущая версия 1.0.1 в проверенных границах Edge/Windows; следующий шаг — P7-01. `src/music`, `src/training` и `src/audio/plan.ts` — чистые модули; `src/audio/engine.ts` владеет Web Audio, `src/storage` — схемой 2/миграцией, IndexedDB и подтверждённым кешем, `src/app/write-queue.ts` — очередью, `src/app/writer-lock.ts` — одной пишущей вкладкой, `src/main.ts` — координацией. Действуют D-018/D-019/D-021; расширения D-020/R-016–R-020 приняты, продуктовые модули не реализованы. `experiments/p1` — исторический стенд; `experiments/p7-scale/after-fix.json` — синтетическая проверка фактического продукта без подмен. Команды — в [DEVELOPMENT](docs/DEVELOPMENT.md), результаты — в [P7-00](docs/verification/P7-00.md). Перед работой определяй состояние по файлам и Git.

## Требования и решения

- Учитывай актуальные инструкции пользователя. Предложение в документации не является утверждённой возможностью или фактом реализации. Явная команда пользователя может авторизовать соответствующую разработку; не создавай дополнительное согласование только из-за старой метки «Предложено».
- Если новая задача меняет предпосылки, обнови связанные документы и объясни существенное изменение. Неразрешённую продуктовую развилку опиши с рекомендуемым вариантом, последствиями и способом проверки.
- Существенные решения записываются в единый `docs/DECISIONS.md`. Отдельные ADR-файлы не создавать. Историю заменённых решений сохранять со ссылкой на новые записи.
- Статусы задач менять по фактическому результату. Наличие описания или тестового плана не означает завершение реализации.

## Изменения

- Сначала изучи затрагиваемый код и инструкции, если они уже появились. Сохраняй изменения пользователя; не сбрасывай рабочую папку ради чистого состояния.
- Делай изменения в рамках задачи. Полезные идеи из аналогов не добавляй в первую версию автоматически.
- Обновляй основной источник информации: поведение — требования; порядок работ — план; устройство — архитектура; обоснование — решения; внешние основания — исследование. В остальных документах используй ссылки.
- Сохраняй стабильные идентификаторы требований, задач и решений. Не перенумеровывай старые записи после вставки новых.
- Используй русский язык для документации и интерфейса. Идентификаторы, названия технологий и форматов сохраняй общепринятыми.
- Новые технические зависимости обосновывай реальным сценарием; проверь первичную документацию, ограничения и условия включения ресурсов в поставку.

## Проверки

Для изменений документации: проверить относительные ссылки и якоря, согласованность ID/статусов, актуальность затронутых источников и отсутствие ошибочного описания будущего как реализованного. Проверить пробелы командой `git diff --check`; для подготовленного коммита — `git diff --cached --check`.

Для кода определить команды по существующей конфигурации и выполнить проверки, соответствующие изменению. Приложение использует корневой package.json, стенд P1 — свой в `experiments/p1`. Для музыкальной логики использовать независимые контрольные примеры из R-014; для звука отдельно проверять расписание и поведение браузера; для данных — экспорт/восстановление и отказ без частичной записи.

При изменении заданий проверять самостоятельный первый ответ отдельно от исправления/показа/пропуска, дубликаты «найди все», исходный контекст результата и отмену сессии при смене параметров или режима. Недопустимый диапазон не должен молча использовать старый корректный контекст. Скрытие карты и названий ответов в ARIA проверяется пользовательскими сценариями; не создавать скрытый тестовый API с правильными ответами.

При изменении звука проверять чистый план, фактический live-сигнал, PCM и UI отдельно. Запланированное событие ещё не означает прозвучавшее: исключать `cancelled` и сравнивать время с текущими аудиочасами. После дробной паузы проверять непрерывность сетки и маршрута; конечный проход завершается по `finishAt`, а не при раннем callback. Реальное скрытие вкладки проверяется отдельным Edge/CDP без эмуляции фокуса. Тестовый `window.p4` разрешён только изолированной fixture, в приложении его нет. Физическую задержку и качество тембра нельзя выводить из PCM.

При изменении данных проверять строгую валидацию всего снимка, исходный контекст/часовой пояс/локальную дату и раздельные screen/manual результаты. Импорт до подтверждения не меняет базу или занятие; подтверждённая замена проходит одной транзакцией. Для rollback нужен abort после уже успешного put, а не только отказ до записи. Ошибка записи остаётся видимой до успешного повтора; экспорт ждёт очередь и не выдаёт несохранённое за записанное. Тестовые `window.p5`/`window.p6` существуют только в fixture. Не подменять нативную IndexedDB памятью в проверке постоянства/квоты. Изменение схемы требует новой версии и настоящего upgrade старой базы; буквальный v1 fixture и события/даты сохранять. Два продуктовых писателя не допускаются: проверять Web Locks, передачу права, retiring guard и запрет поздней инициализации. Поддержка одной вкладки не означает совместное редактирование. Схемы P1 и продукта не смешивать.

Не добавляй вымышленные команды запуска, библиотеки, замеры задержки или результаты тестов. Инструкции расширяются фактически выполненными командами; сохраняй различие между экспериментом и продуктовой реализацией. Автоматические результаты в `test-results` и `experiments/p1/results` игнорируются Git; проверенный снимок переносится в `docs/verification` вместе с отчётом. В unit JSON допустима нормализация путей, но не изменение исходов, ошибок или числа тестов.

Кеш данных обновлять только после commit; отказ, quota и abort не меняют подтверждённый снимок. По умолчанию `readSnapshot()` возвращает замороженный известный снимок одного писателя; явный `fresh:true` обязан прочитать/валидировать IndexedDB. Проверять кеш отдельно от свежего чтения и независимого raw IDB, включая неожиданное закрытие соединения после очистки только тестового origin. Закрытая панель истории не должна строить карточки после каждого ответа; upsert сохраняет ID сессии. Предел JSON — 64 МиБ UTF-8, это не обещание доступной RAM/квоты. Не выдавать локальный синтетический benchmark за SLA или полную приёмку будущего слухового модуля.

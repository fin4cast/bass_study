## Как пользоваться планом

- Статусы задач: **не начата**, **в работе**, **выполнена**, **заблокирована**. Для блокировки указывать конкретную причину и действие, которое её снимает.
- Задача выполнена, когда получен указанный результат и пройдена её проверка. Начатая работа или написанный код сами по себе этого не подтверждают.
- В задаче указывать идентификаторы требований вместо повторения их полного текста. Изменение поведения сначала отражается в требованиях, изменение подхода — в журнале решений и архитектуре.
- При поступлении явной задачи на реализацию сверять её с текущим предложением MVP. Новое указание пользователя может утверждать или менять соответствующий объём без дополнительного общего согласования.
- Пользователь поручил автономно продолжать последующие этапы плана после завершения текущего ([D-014](DECISIONS.md#d-014)). После проверенного результата переходить к следующей готовой задаче; подробные критерии ещё не определённых расширений уточнять при входе в соответствующий этап.
- План не содержит календарных обещаний. Оценки можно добавить после выбора объёма и первых технических проверок.

[D-020](DECISIONS.md#d-020) принимает ограниченные сценарии [R-016–R-020](REQUIREMENTS.md#r-016); более широкая таблица R-015 остаётся идеями. P7-00 завершён по [D-021](DECISIONS.md#d-021) и [отчёту](verification/P7-00.md); остальные модули ещё не прошли продуктовую приёмку. Каждый имеет собственную проверку и checkpoint; наличие строк не обещает автоматическую оценку игры.

| Задача | Сценарий и результат | Зависимость | Условие завершения | Статус |
|---|---|---|---|---|
| P7-00 | Компактный JSON до 64 МиБ, постепенное обновление подтверждённого снимка/сводок и lazy history; R-012/R-014 | Проверенный P6, схема 2; [исследовательская проба](RESEARCH.md) | Годовая синтетическая модель нативно восстановлена/экспортирована без потери событий/дат. Кеш меняется после commit, fresh/raw чтения и отказ/clear проверены; закрытая история не строит карточки после ответа, upsert сохраняет ID. Первое полное чтение остаётся отдельной медленной фазой | Выполнена |
| P7-01 | Добавить слуховой ответ по 1/3/5 мажорного и минорного трезвучия; R-016 | P7-00; задания, аудиособытия и история P6 | Независимы опорная тоника/цель, ответы не раскрыты картой/ARIA, replay отмечен отдельно, показ/ошибка/пропуск не завышают самостоятельность; план/PCM/UI и перенос результатов проверены | Не начата |
| P7-02 | Собрать короткий маршрут гриф → слух → последовательность с ориентиром 10 активных минут; R-016 | P7-01, существующий плеер | Цели/переходы трёх блоков понятны, пауза исключена из активного времени, прерывание хранит фактический материал; нет обещания фиксированного настенного времени или общего «уровня» | Не начата |
| P7-03 | Сыграть четыре такта C–F–G–C: бас 1–3–5–3, pad, клик; R-017 | P7-00; общий аудиоплан/transport P6 | Один ход времени, независимые mute/громкости, проверенные аккордовые ноты, границы тактов/циклов и старт/пауза/стоп; эталоны плана, PCM и UI совпадают | Не начата |
| P7-04 | Показать одну существующую последовательность в басовом ключе и четырёхлинейном TAB; R-018 | P7-00; стабильные позиции/события P6 | Выбор способа рисования обоснован басовыми примерами; written = sounding + 12, фактические струны/лады, три длительности и подсветка наступившего события проверены; нет отдельного transport или импорта партитур | Не начата |
| P7-05 | Подключить один локальный файл или до четырёх подготовленных stems; R-019 | P7-00, проверенные часы/жизненный цикл аудио | Общие нуль/seek/пауза/[A,B), независимый mixer и реальные импульсные эталоны при rate=1; JSON содержит только metadata/cues и требует повторного выбора файлов. Varispeed явно меняет высоту; time-stretch и разделение инструментов не обещаются | Не начата |
| P7-06 | Исследовать добровольно включаемый аудиовход, уровень и диагностическую частоту; R-020 | P7-00; отдельный исследовательский протокол входа | Разрешение только по кнопке, ошибки/уровень/неопределённость понятны, tracks освобождаются; независимые низкие ноты/шум/гармоники испытаны. Граница между синтетическими результатами и необходимой калибровкой реального баса явно записана; автоматического зачёта нет | Не начата |

Рекомендуемый порядок — P7-00 → слух/короткий маршрут → сопровождение → нотация → личные записи → диагностический вход. Общая инфраструктура не должна отложить полезный небольшой модуль ради всех направлений сразу. Для P7-06 отсутствие реального устройства не даёт права объявлять физическую точность подтверждённой: можно завершить диагностический интерфейс и синтетический протокол, а калибровку оставить явным ограничением до испытания пользователем. Включение аудиооценки требует отдельного решения.

Итог P7-00: размер и обычный путь ответа проверены отдельно от стартового полного чтения; результаты относятся к локальным синтетическим данным, не SLA. Входные условия P7-01 выполнены: стабильные история/резервная копия, правила оценки и аудиовывод. Чистые заготовки нового модуля сами по себе не закрывают R-016: нужны настоящий звуковой cue, UI без утечки ответа и перенос нового типа результата.

Пятиструнный бас, нестандартные строи, телефон, редактор партитур, автоматическое выделение инструментов и гарантированное сохранение высоты при замедлении не входят в эти ограниченные задачи. Они требуют отдельных требований и приёмки.

## Как продолжить из нового чата

1. Прочитать [AGENTS](../AGENTS.md), цели и актуальные требования; проверить состояние репозитория.
2. Найти первый незавершённый этап и его зависимости. После P7-00 — P7-01: слуховой ответ по 1/3/5 с независимыми аудио/UI-проверками и достоверной историей нового результата.
3. Сопоставить новую задачу пользователя со статусами требований и решений; обновить объём там, где он явно изменён.
4. Реализовать ограниченную задачу, выполнить её проверки, записать фактический результат и обновить затронутые документы.

Не отмечать последующий этап завершённым по одному работающему экрану. При изменении подхода сначала сохранить основания в журнале решений, затем согласовать с ними архитектуру и оставшиеся задачи.
